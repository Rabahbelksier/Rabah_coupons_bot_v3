---
name: AI intent composition
description: Design rule for interpreting Telegram product-search requests with a primary goal plus independent filters.
---

The AI search intent is compositional: `trending`, `product_best`, and the other request types describe the primary goal, while user-requested category, product keywords, multilingual synonym groups, price bounds, RAM, storage, shipping country, and price direction remain independent filters. For Gemini product intents, an inferred internal family is a hard filter only when the user explicitly requested a category. Provider fallbacks must preserve a specific product request as a product search rather than broadening it into a category search. A valid product or broad-price request with no accepted cache keyword is a supported search with no results, not an unsupported request. Gemini may match a user's product meaning to candidate vocabulary across languages, but each emitted keyword and synonym must normalize to one complete cached phrase; underscores and spaces are equivalent, and alternatives for one concept remain grouped as OR matches. Deterministic Arabic parsing must validate model output for price, shipping, broad-search, and generic-word semantics. AliExpress second-level categories remain authoritative when they map to a known family. A non-empty official subcategory with no internal mapping belongs to the `other` catch-all only when `other` is requested; it must not erase an exact product match or broaden a known category. AI category fallback is allowed only when the source subcategory is absent or invalid.

**Why:** Model output previously leaked words such as “سعرها” into product matching and dropped colloquial price/shipping forms, causing valid rows to be rejected. Provider fallback output could classify distinct product phrases under the same broad category, and a cache miss was incorrectly shown as an unsupported feature instead of a normal no-results response. Requiring a cached product term to appear in the user's language caused false misses, while accepting arbitrary translations could broaden results; semantic selection from cached terms addresses both risks. Multilingual alternatives must behave as OR matches rather than requiring every translation in an offer title. Title-only category inference also confused accessories containing words such as “phone” with actual phones. An unrecognized but present AliExpress subcategory can still be valid source taxonomy; treating it as a hard mismatch suppresses exact matches in the `other` family, while guessing from the title could send it to an incorrect category.

**How to apply:** Preserve every explicit constraint. Use structural validation to distinguish a product request from a category request, while taking product terms only from the permitted provider vocabulary. For Gemini, use semantic cross-language selection only among active cached phrases, require every returned phrase to match a complete vocabulary entry after underscore/space normalization, and retain one OR group per concept. For Groq, OpenRouter, and Cloudflare, keep multilingual alternatives grouped by concept and match one alternative per group; do not flatten synonyms into mandatory AND terms. Route valid no-match intents through database search so the user receives the no-results response; reserve the supported-intent help text for genuinely unsupported requests. For database search, match a mapped second-level family exactly; when an official non-empty subcategory has no family mapping, allow it only for the `other` catch-all, not for known families. Keep this taxonomy rule for ordinary mapped searches; dedicated channel-offer labels use internal AI category keys as described in [channel offer category keys](channel-offer-category-keys.md). Enforce price bounds after matching and deduplicate broad searches by product model using the same requested price direction.

For product searches only, an exact complete cached phrase in the title may survive an unmapped official subcategory when title-based classification confirms the requested family. Do not use this exception for category-only searches, non-exact phrase matches, or rows with a mapped conflicting official category.

**Why:** The product parser can infer a category from the matched cached phrase, but AliExpress can store the same offer under an official subcategory that has no internal category mapping. Applying the strict category filter then discards an otherwise exact product match.

**How to apply:** Keep this exception in the product-title match path, require a complete phrase match plus title-local family evidence, and leave all explicit price/spec/shipping filters and category-only taxonomy behavior unchanged.

For Gemini product requests, only apply the internal `category` field as a hard filter when `category_filter_requested` is explicitly true. If it is explicitly false, discard the inferred category after the request has been normalized to a product intent; a missing flag is not false. Preserve closed-vocabulary keyword matching and every other explicit filter. Do not change category-only requests or other providers.

**Why:** Real searches for car diagnostic scanners and a tire inflator had exact cached-phrase title matches, but Gemini inferred unrelated internal families while marking category as unrequested. Treating those guesses as user constraints removed every matching offer.

**How to apply:** Preserve the flag's presence separately from its value, and gate the behavior to Gemini product request types. Keep explicit category matching fail-closed and leave price, shipping, specifications, and offer-type constraints untouched.

For direct Gemini product intents, keep the first-pass result when at least one specific cached product phrase survives validation. Run the focused semantic selector only when no specific product phrase survives, and skip it for explicit category-only searches. Keep the second response restricted to its exact cache snapshot and preserve all parsed filters.

**Why:** A focused retry can recover semantic misses without doubling Gemini latency and quota for searches that already selected a specific cached phrase.

**How to apply:** Decide after closed-vocabulary validation and product-intent detection. If the retry fails, retain only exact cached primary terms or return no results; never broaden the search.

For provider-backed user searches, have the AI produce one canonical Arabic search request before its structured intent, preserving every explicit product/category, price, specification, shipping, and offer-type constraint. Use that canonical request for downstream local validation and secondary semantic matching; keep the original wording only as the provider's source input and for provider-unavailable fallback.

**Why:** The user requires semantically equivalent phrasings to lead to the same supported search without depending on exact words in the original message. A provider's normalized request must also prevent later local heuristics from reclassifying the same request based on its surface wording.

**How to apply:** Keep canonicalization in the existing primary provider call, preserve named products and models, and derive structured fields from the canonical request. Do not add a second provider request or change unrelated search and database behavior.
